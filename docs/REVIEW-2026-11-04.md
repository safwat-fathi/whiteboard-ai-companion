- Trigger: server mode (`NEXT_PUBLIC_API_BASE` set), board with >= 501 unlocked elements; Ctrl+A then Delete.
- Path: `select.ts:362-368` selects all; `select.ts:379-381` -> `deleteBatch` (`transform.ts:157-161`) builds ONE batch with one `remove` per element. `Editor.commit` applies it locally (`editor.ts:304-317`), the sync client sends it (`sync.ts:92-97`), the server's `checkLimits` rejects `batch.ops.length > 500` (`apps/server/src/limits.ts:6,24-25`, called at `board-service.ts:134`; the reject message goes out at `gateway.ts:126`), the client rolls the whole thing back and shows "A change was not accepted: ..." (`sync.ts:170-180`).
- Same for dragging / nudging a >500 marquee selection (`transform.ts:131-155`), multi-resize (`select.ts:301-303`), Arrange menu (`SelectionToolbar.tsx run()`), `groupBatch` of >500 units. Only the eraser chunks (`eraser.ts:8,54-60`, comment "the server caps a batch at 500 ops").
- Nothing documents it (engine doc: "A batch ... is the unit of undo"; PLAN #40 states the cap only server-side).
- Fix: chunk in `Editor.commit`/a helper for every bulk builder, or raise the cap; document.

**B-02 (low) A batch the server rejects leaves a phantom undo entry.**
- `Editor.commit` records the undo entry before the server has accepted anything (`editor.ts:312`); `sync.ts:onReject` (`:170-180`) rolls the scene back but never touches `editor.undo`.
- Trigger: any reject, e.g. B-01 or a >1 MiB frame (`sync.ts:83-86`). Next Ctrl+Z pops the phantom: its inverse targets state that no longer matches, `UndoManager.filter` (`undo.ts:129-166`) drops every op (adds that exist, patches whose current value differs from `wrote`), the batch is empty, `Editor.replay` returns silently (`editor.ts:351-352`). Ctrl+Z "does nothing" once, with no message (see D-07).
- Fix: on reject, remove the entry for that `batchId` from the stack (needs an `UndoManager.discard`).

**B-03 (low-medium, hostile or buggy client only) `z` is not validated as a fractional index; one bad `z` makes every later "add" throw.**
- Schema: `schema.ts:198` `z: z.string().min(1)` and `reorder.z` `:266-269`; `apps/server/src/limits.ts` has no z check. `ordered()` sorts by plain string compare (`scene.ts:24-27`) so e.g. `"~"` sorts last.
- Confirmed: `generateKeyBetween('~', null)` with the repo's `fractional-indexing@4.0.0` throws `invalid order key head: ~` (also `'!'`).
- Trigger: a WebSocket `ops` batch `{op:'add', el:{... z:'~'}}` is accepted. Afterwards every creator that does `zBetween(ordered(scene).at(-1)?.z, null)` throws: shape/text/chart/ink/math tools (`shape.ts:47-52`, `tools/text.ts:190`, `chart.ts:43`, `ink.ts:84`, `tools/math.ts:221`), `addImages` (`editor.ts:504-509`), `groupBatch` (`group.ts:93`), and every tutor write tool via `stackAbove` (`tools/make.ts:7-13`). The board stops accepting new elements until the offending element is deleted.
- Origin/Host-checked localhost makes this a robustness gap rather than an exploit; it is exactly the "server trusts core zod schemas" case.
- Fix: refine `z` with the library's key validity (try `generateKeyBetween(z, null)` in a `.refine`).

**B-04 (low-medium) Quadratic text layout on adversarial but schema-legal text.**
- (a) `text.ts:17` `trimBreak = s.replace(/[ \t]+$/, '')` is O(run^2) when a run of spaces/tabs is followed by a non-space. `push`/`measure` call it on every row (`text.ts:84,90`). Replica timings (`scratchpad/review/probe-text.mjs`): "x" + 10,000 spaces + "y" 152 ms, 20,000 -> 598 ms, 40,000 -> 2,397 ms per call (x2 per row), so the schema/textarea cap of 100,000 chars (`schema.ts:49`, `tools/text.ts:121`) is about 15 s per layout, extrapolated.
- (b) `text.ts:102-117`: the grapheme search for a word wider than the line is O(n^2 / k). `maxWidth` has no minimum (`schema.ts:53` `size.optional()`, >= 0). Replica: one unbroken word with `maxWidth: 0`: 10,000 chars 0.33 s, 20,000 -> 1.3 s, 40,000 -> 5.2 s; 100,000 chars is roughly 30 s extrapolated. This is the same shape as the flaky "10,000-char single word" test noted in PLAN #52(e) (1.07-1.34 s in the repo's real measure).
- Reach: a human can paste a big whitespace run (a), and the tutor's `update_elements` accepts `data.text` up to 100k and any `data.maxWidth` (`tools/board.ts:397-399`, no limits as `add_text` has at `:185,193-198`) and runs `layoutText` **synchronously on the server** (`tools/board.ts:518`), so it blocks the Node event loop. A WS client can send both directly.
- Also: while a text is open for editing, `Tool.onFrame: sync` (`tools/text.ts:174`) calls `withText` which builds a new element object each time, so the identity-keyed layout memo (`text.ts:15`) misses and the whole text is re-laid-out every frame and keystroke.
- Fix: trim with a loop from the end instead of the regex; cap `maxWidth` below at, say, one em in the schema (and `update_elements`); bound the grapheme search or memoise by text+width.

**B-05 (low) The browser math provider's cache is unbounded, and failures are cached for the session.**
- `apps/web/src/editor/math.ts:19` `entries = new Map()`; `entries.set` at `:57,65,164`, never deleted. Every distinct `(latex, display, colour)` ever requested stays, holding its SVG string and parsed paths. The equation editor requests a render for each debounced edit state (`MathEditor.ts:15,170-213`), so a long editing session accumulates one entry per pause. `packages/math/src/index.ts:38,52-55` caps its own cache at 2,000 but the browser provider does not use `peekMath` (D-14).
- Failure entries are also permanent (`math.ts:57-61,65`; `index.ts:121-126`): a transient dynamic-font chunk load error becomes a red error on that formula until reload.
- Fix: LRU (e.g. reuse `store`/`peekMath` from `packages/math`) and do not cache load errors.

**B-06 (low) Unknown keys survive whole-leaf patches (validation output is discarded).**
- `ops.ts:54-71` checks each `set` value with `safeParse` but throws the parsed result away; `scene.ts:106-119` assigns the raw value (`setPath` -> `structuredClone(value)`), runs `ElementSchema.safeParse(el)` only as a check (`:113-118`) and stores the pre-parse `el` (`:119`). zod 4 objects strip unknown keys on parse (verified on zod 4.6.7), so `{"op":"patch","id":X,"set":{"data":{"kind":"rect","junk":"...900 KB..."}}}` (or `"style"`) persists `junk` in the live scene, ops log, snapshots and broadcasts. `add` is safe because `validateBatch` returns the parsed output.
- Impact: storage amplification past the documented per-field limits (bounded only by the 1 MiB frame). Fix: store `r.data` in `applyBatch`.

**B-07 (low, UX) Adding a formula before MathJax has answered creates a second, undocumented undo step.**
- `tools/math.ts:82-99,108-109,155-157`: when the formula is committed before the renderer replies (first formula of a session, fast typing), `fitWhenReady` later commits a separate `Fit Math` batch (patch `w`,`h`). Ctrl+Z right after adding then undoes the refit, not the add, and the extra batch is synced.
- Fix: await the renderer before the Add commit, or fold the refit into the add.

**B-08 (low) A transient blob fetch failure marks an image "missing" for the whole session.**
- `images.ts:211-214` `missing.add(blobId)` when `store.get` returns undefined; `blobs-http.ts:61-70` returns undefined on any network error or non-OK status, so one blip is indistinguishable from a 404. `peek` then returns `'missing'` forever (`images.ts:188`), drawing "missing image" until a reload (also for `createImageBitmap` failures, `:242-245`).
- Fix: only remember a real 404, or expire the entry.

Suspected, not shown (what to check):
- S-1: `importImage` (`images.ts:148-157`): if `reencodeInBrowser` returns null (no `convertToBlob` and no `toBlob`) the original un-downscaled bytes are stored while `naturalW/H` are the downscaled numbers. Needs a browser without both APIs; check by stubbing them in `images.test.ts`.
- S-2: `render.ts:594-607` oversize (> 4096 px) math whose SVG `svgToPaths` rejects: the browser `bitmapFor` returns the predecoded bitmap once and deletes it (`math.ts:111-118`), so successive frames may alternate blank / drawn.
