# S4 embeddings and search: result

## Environment

search.commit: measured at bee787c (the committed spikes/s4-search/latency.ts and topk.ts, four runs, working tree clean apart from the unrelated docs/plans/deployment.md); the commit that adds these lines changes only this file
search.machine: MacBookAir10,1, Apple M1 (4 performance + 4 efficiency cores), 8 GB, macOS 27.0.1 (arm64), AC power, Low Power Mode off, no thermal or performance warning recorded
search.toolchain: Node 22.21.1, pnpm 12.8.1, tsx 4.23.15, better-sqlite3 13.0.3 (SQLite 3.53.4), run as `pnpm --filter s4-search latency` (`tsx --expose-gc latency.ts`)
search.fts5: `select sqlite_compileoption_used('ENABLE_FTS5')` returns 1 (asserted at the start of every run; the script throws otherwise)
search.nativeBuild: `pnpm approve-builds better-sqlite3` printed "not awaiting approval" and still wrote `better-sqlite3: true` to `allowBuilds` in pnpm-workspace.yaml (next to `esbuild: false`); better-sqlite3 13.0.3 ships prebuilds (darwin-arm64/x64, linux-arm64/x64, linuxmusl-arm64/x64, win32-arm64/x64) and has no install script, so the setting changes nothing today: it loaded and passed `pnpm install --frozen-lockfile` before the approval too, and on a VPS of another arch or libc nothing would compile it
search.backgroundLoad: the Mac was not idle in any run. `top` before runs 1 and 2: WallpaperAerials about 39% of a core, WindowServer 25%, VTDecoderXPCService 10%, kernel_task 6%; after run 4: WallpaperAerials 38%, an unrelated process named "deleted" 28%, WindowServer 26%, triald_system 21%. ANECompilerService, which used about 77% of a core earlier in the session, was not in the top list. 1-minute loadavg at the start of the four runs: 3.29, 3.39, 3.44, 3.22
search.memoryPressure: the Mac was short of memory throughout (swap 3.7 GB of 5 GB used, 3,716 to 3,724 MB; compressor holding 278k to 363k pages over the session; free memory about 60 MB to 1 GB depending on when it was sampled). The Float32Array alone is 390.6 MiB; an RSS delta below that (387.2 MiB in run 2) is macOS compressing or swapping resident pages out, or reusing pages it kept from an earlier free; the two were not separated
search.rssMacOS: macOS keeps freed pages in RSS. Scratch check (not in the repo): fill a 390 MiB Float32Array inside a function, return, run gc twice: process.memoryUsage().arrayBuffers 0.0 MiB, RSS still 435.4 MiB (38.5 MiB at the start), and unchanged 1 s later. So an RSS delta taken after something was freed is not a measurement of the new allocation; the delta of the load below ranges from -19 to +91 MiB for that reason, and the figures to read are the array size and the peak RSS. On Linux, freed memory is returned and the delta is real
search.vectors: synthetic, 1024-d, unit length (components uniform in [-1,1) from a seeded mulberry32, normalised in place), one Float32Array per N, row-major; 5 warm-up and 50 timed queries per N, each a different random unit vector
search.method: `topK(vectors, dims, query, k)` in topk.ts: for each row four independent dot-product accumulators over the typed arrays, then a k=8 descending insertion list (a candidate is compared with the current 8th score first, so most rows cost one comparison). Timed with performance.now() around each call; p50 and p95 are nearest-rank over the 50 timed calls. RSS delta is process.memoryUsage().rss after the last query minus RSS after two forced GCs before the vectors were allocated (so it holds the vectors, the 55 queries and the JIT state they cause). Peak RSS is process.resourceUsage().maxRSS (the whole process, kB converted to MiB)
search.selfCheck: before any timing, topK is compared with a full sort on 3,000 random 128-d rows (same indices, scores within 1e-9), a planted row returns itself with score 1, k > n returns n rows, k = 0 returns nothing, and dims % 4 != 0 throws
search.coldStart.method: 100,000 rows of 4,096 B (one 1024-d vector each) inserted into `chunks(id integer primary key, embedding blob)` in one transaction (WAL, synchronous NORMAL, the app's pragmas), connection closed. The latency runs and this write live in one function, so that nothing holds the 390.6 MiB array when it returns. Then, after two forced GCs, the script reads process.memoryUsage().arrayBuffers and throws if it is above 64 MiB (it was 1.5 MiB in all four runs, so only the new array is resident during the load). A new read-only connection runs `select embedding from chunks order by id` with `.raw().iterate()` and copies each BLOB into one preallocated Float32Array (no array of 100,000 Buffers). The time covers opening the DB, the statement and the copy. The loaded array is checked by running the same probe query as on the original: identical top-8 indices and scores
search.coldStart.cache: the OS page cache is warm (the file was written seconds earlier); a true cold read from disk is not measured here (no sudo purge)
search.dbFile: spikes/s4-search/data/synthetic.db, 439.6 MiB, gitignored through `data/`, deleted after the runs; each run deletes and regenerates it

search.exact.scaling: about 0.8 ms per 1,000 vectors at 1024-d (p50 79.5 to 79.7 ms for 100,000, 7.95 for 10,000, 0.48 for 600), i.e. linear; one book of 600 chunks costs 0.5 ms, 200 times under the 100 ms budget
search.exact.headroom: the worst p95 for 100,000 vectors is 83.560 ms (run 2), 16.4 ms (16.4%) under the 100 ms limit, and the slowest single query was 92.141 ms (run 3), on this M1 with the background load above. The VPS figure comes from Task 5, which reruns this script
search.exact.dims: these numbers are for 1024-d vectors only. The scan does one multiply-add per component, so cost grows with dims: about 1.5x at 1536-d (about 120 ms for 100,000 vectors, over the limit) and 4x at 4096-d (about 320 ms) by arithmetic, not measured; the vectors grow the same way (100,000 x 1536 x 4 B = 585.9 MiB, over the 512 MiB cap; x 4096 = 1,562.5 MiB). Task 7 must re-evaluate both for whichever embedding model it picks
search.exact.memory: 100,000 x 1024 x 4 B = 409.6 MB = 390.6 MiB of vectors. The script's limit is 512 MiB (121 MiB of margin); read as 512 MB (488.3 MiB) the margin is 98 MiB, and 409.6 MB passes either way. At 4 KiB a chunk, 512 MiB holds 131,072 chunks (488.3 MiB holds 125,000)
search.peakRss: the process high-water mark at the end of a run was 533.3 to 550.3 MiB (534.7, 533.3, 550.3, 541.6), against 78.5 to 78.8 MiB at the start of the script (Node, tsx and the imports). The 390.6 MiB array accounts for most of the rest; the remainder (about 70 to 80 MiB) was not broken down (V8 heap, the query arrays, SQLite, pages macOS kept from the 600 and 10k arrays). The load raised the peak by 0 to 14.5 MiB over what the latency runs and the write had already reached (534.7 -> 534.7, 533.3 -> 533.3, 535.8 -> 550.3, 539.3 -> 541.6), because only one 100k array is resident at a time. The peak is not gated; the 512 MB cap is on the vector cache, not on the process
search.coldStart.write: 100,000 rows in one transaction in 1,907 to 2,372 ms (2,201 / 2,372 / 1,907 / 2,065), file 439.6 MiB
search.coldStart.load: 100,000 rows into one Float32Array in 236 to 351 ms (236 / 351 / 236 / 348); page cache warm, so this is the lower bound of a cold start. The rss before -> after of the load is in the run lines above and is not a usable delta on macOS (see rssMacOS)
search.coldStart.roundTrip: top-8 of the probe query on the loaded array equals the top-8 on the original array (checked in all four runs)
search.history.scalarTail: the first version of topK had a scalar tail loop for dims not a multiple of 4; N=100,000 then measured p50 93.9 ms and p95 94.2 ms (one run). Removing the tail loop (dims % 4 != 0 now throws) cut it to 79 ms. In a stand-alone micro-benchmark a one-accumulator loop took 97.6 ms, four accumulators 72.4 ms and eight 77.5 ms (top-1 only, constant dims), and a Float64Array query was slower (115 to 132 ms); four accumulators is what topK uses
search.history.coldStartRetracted: five runs at 47b89e0 (N=100,000 p95 79.563 to 83.800 ms, matching the figures above) reported a cold-start load of 262 to 277 ms with an RSS delta of 398 to 410 MiB. Those two figures are void: the write array was still referenced (by a const that the write transaction captured, and, as the new ArrayBuffers check showed when only that was fixed, by the top-level frame holding the last loop iteration's array), so the load ran with two 390.6 MiB arrays resident (about 780 MiB); the "about 15 MiB above the array" remark made then rested on the same runs. Replaced by the bee787c figures above; the N <= 100,000 latency figures were taken before that point and were not affected
search.recall.corpus: 3 books (`ck12` 651 pages / 718 chunks via R1; `alg1` 700 pages / 751 chunks via R1; `arabic` 40 pages / 40 chunks via R3 `mistral-ocr`, where each `annotations[0].file.content` text element between `<file>` and `</file>` is one page), 10 questions per book (`eval/{ck12,alg1,arabic}.jsonl`, 30 total; `ck12` uses `"numbering": "printed"` mapped via `getPageLabels()` offset +6). Total S4b embedding spend: $0.0274 of $0.50 ceiling (+ $0.0625 R3 OCR for the 30 additional Arabic distractor pages)
search.recall.bm25: k=5 / 8 / 12 recall (MRR) — ck12: 80% (0.675) / 90% (0.692) / 100% (0.700); alg1: 100% (0.870) at all k; arabic: 70% (0.508) at all k; overall k=8: 86.7% (0.690)
search.recall.bge_m3: `baai/bge-m3` (1024-d, $0.0058 total) — vector@8: ck12 100% (MRR 1.000), alg1 100% (1.000), arabic 100% (0.842; @5 90%), overall 100.0% (MRR 0.947). hybrid@8 (RRF k=60): ck12 100% (0.775), alg1 100% (0.883), arabic 80% (0.583), overall 93.3% (MRR 0.747); with ±1 chunk neighbours (`hybridNeighbors8`): arabic 90% (0.762), overall 96.7% (0.838)
search.recall.qwen3_8b: `qwen/qwen3-embedding-8b` (4096-d, $0.0070 total) — vector@8: ck12 100% (0.950), alg1 100% (0.950), arabic 100% (1.000), overall 100.0% (MRR 0.967). hybrid@8: ck12 100% (0.753), alg1 100% (0.883), arabic 80% (0.733), overall 93.3% (MRR 0.790); `hybridNeighbors8`: arabic 90% (0.750), overall 96.7% (0.828). 4096-d is 4x the memory and scan cost of 1024-d (exceeds S4a's 512 MiB / 100 ms budget at 100k chunks)
search.recall.te3_small: `openai/text-embedding-3-small` (1536-d, $0.0118 total) — vector@8: ck12 100% (0.950), alg1 100% (1.000), arabic 100% (0.639; @5 80%), overall 100.0% (MRR 0.863). hybrid@8: ck12 100% (0.750), alg1 100% (0.883), arabic 80% (0.532), overall 93.3% (MRR 0.722); `hybridNeighbors8`: arabic 90% (0.662), overall 96.7% (0.815). 2x cost of `bge-m3`, weaker Arabic MRR (0.639 vs 0.842), and 1536-d exceeds S4a's 100k budget
search.recall.notes: (1) `pdfjs-dist` emits raw `\x01` control chars and PUA glyphs (`\uE000-\uF8FF`) on math pages (`ck12` p. 329+) that must be stripped before chunking/embedding; (2) `baai/bge-m3` with `data_collection: 'deny'` returned transient HTTP 429 ("engine is currently overloaded") on 5 of 24 batches, all succeeding on the first retry after 1.5 s backoff — M4's ingestion worker must retry 429/5xx with backoff

k: 8
